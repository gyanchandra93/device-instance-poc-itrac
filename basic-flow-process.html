Quick memory sheet

The story in one page

Imagine a person is building a list of devices for a project. They pick materials, create templates, rename groups, hide rows, and so on. Then they close the browser tab by accident — or refresh the page — before pressing the final “Create All” button.

Without this system, all of that unfinished work would disappear. With this system, the page quietly keeps a personal notebook of their unfinished work on their own computer (in the browser’s storage). When they come back, the page opens that notebook, compares it with the latest official records from the company server, carefully stitches the two together, and puts the person back where they left off as much as possible.

Everyday analogy Think of the company server as the official project binder in the office. The browser storage is a sticky-note pad the person keeps in their pocket. The persistence folder is the assistant who:
  1. copies important sticky notes into the pocket pad while they work,
  2. opens the pad when they return,
  3. checks the official binder for updates,
  4. merges “my notes” with “official binder”,
  5. and, when needed, asks the office to update the official binder to match.

This folder does not draw the tables on the screen. It does not decide button labels. Its only job is: remember unfinished work, restore it safely, and keep the official records in sync when that makes sense.

What happens when someone opens the page

This is the long path — the one that runs when the page first loads (or after a materials refresh). Read it top to bottom like a journey.

1
Wait until the official data arrives

The page first asks the company server for the latest materials, templates, and subclass names. The “save my work” system does not start merging until that official data is ready. Otherwise it would be guessing.

2
Open the personal notebook

The filing-cabinet file (draftStorage) looks for a notebook belonging to this user and this project. If none exists, it starts with a blank notebook.

3
Merge materials: notebook vs official list

reconcileMaterials compares every material in the notebook with the official materials list.

  • If a material still exists officially, the person’s saved choices (subclass, override, hide/show) usually win over the older official values.
  • If a normal PPM material disappeared from the official list, we drop it from the notebook. We do not invent it again.
  • If a hand-added “Not in PPM” material disappeared, we mark it as something we may try to recreate later — but only if the notebook still has enough details (name, make, model, subclass, quantity).
4
Recreate missing hand-added materials (if needed)

recreateOrphanCustomMaterials asks the server to create those missing “Not in PPM” materials again. Because the server gives them new IDs, this file also updates the notebook (and any template links) so they point to the new IDs instead of the old ones.

5
Merge templates: notebook vs official list

reconcileTemplates does the same kind of merge for group templates. Saved names, descriptions, parent subclass, instance counts, and friendly device names from the notebook are preferred when the template still exists officially. Template devices that point at materials that no longer exist are removed. Templates that exist only in the notebook (deleted on the server) become candidates to recreate — but only if they still have at least one valid device left.

6
Recreate missing templates (if needed)

recreateOrphanTemplates creates blank templates on the server, fills in the saved details, re-adds the remaining devices, and rewires the notebook so old template IDs become the new ones. Group-instance custom labels tied to those templates are rewired too.

7
Clean up group-instance notes

If someone had customized a Group ID / Group Name for an instance that no longer makes sense (template gone, or instance number out of range), those notes are thrown away. Valid custom labels are kept for the next step.

8
Put the merged result on the screen

The manager hook asks the page’s main state system to load the merged materials and templates. Group Instance custom labels are applied through applyInstanceDraft. The cleaned notebook is written back to the filing cabinet.

9
Push the merged choices to the official binder

syncDraftToApi sends only the differences that still need to be saved on the server (subclass changes, override ticks, hide/show, template field changes, device add/remove/reorder). If some rows fail, those rows fall back to the official values on screen, but the notebook is kept so a refresh can try again. The person sees a clear error message for each failed item.

Who is in charge of this journey? The manager file — useDeviceInstanceDraftPersistence — calls every other file in this order. The other files do not call the manager. They are helpers the manager uses.

What happens while they edit

After the open-page journey finishes successfully, a quieter behavior turns on.

Every time the person changes materials, templates, or group instances, the manager does not write to the notebook instantly. That would be noisy and wasteful. Instead it waits a short moment (about a third of a second) after the latest change. If no new change arrives in that window, it takes a fresh snapshot of the current screen state using buildDraftFromState and asks the filing cabinet to store it.

So: editing feels instant on screen, and the notebook updates a beat later in the background.

When “Create All” succeeds, the manager clears the notebook. The unfinished-work story is over; the official project now owns those devices.

How the files work together

Here is the family map. Arrows mean “this file asks that file for help.”

Manager hook Talks to almost everyone: filing cabinet, snapshot builder, both merge files, both recreate files, and the sync file.
Filing cabinet Does not call the others. Only reads/writes/clears the notebook.
Snapshot builder Uses the subclass helpers to convert readable names into IDs before saving.
Materials merge Uses subclass helpers. Hands orphan candidates to the materials recreate file.
Templates merge Uses subclass helpers. Hands orphan candidates to the templates recreate file. Also provides the “rename GI keys when a template ID changes” helper.
Materials recreate Uses the materials merge’s orphan list. Updates the notebook and template links after new IDs arrive.
Templates recreate Uses the templates merge’s orphan list and the GI-key remapper. Updates the notebook after new template IDs arrive.
Sync to server Uses subclass helpers and compares the merged screen state against the official baseline. Reports failures so the manager can revert those rows on screen.
Apply instance draft Used when the screen rebuilds Group Instances, so custom Group ID / Group Name notes reappear.
Order that matters Materials recreate happens before template merge/recreate on purpose. Templates point at materials by ID. If we recreated templates first, they might still point at dead material IDs. By recreating materials first and remapping IDs, templates can safely link to the new material IDs.

The manager — useDeviceInstanceDraftPersistence

This is the only file that “runs the show.” It is a long-lived assistant attached to the page. It does not draw UI. It decides when to read the notebook, when to merge, when to recreate, when to sync, and when to allow quiet auto-saving while the person edits.

Depends on draftStorage, buildDraftFromState, reconcileMaterials, recreateOrphanCustomMaterials, reconcileTemplates, recreateOrphanTemplates, syncDraftToApi — plus the page’s own state callbacks that put merged data onto the screen.

What each piece inside it does

The main hook itself public

This is the entrance. The page hands it the current official materials/templates, the current on-screen materials/templates/instances, the subclass list, and two “please update the screen” callbacks. In return, the page gets two tools:

  • one for re-running the merge after a materials refresh, and
  • one for wiping the notebook after Create All succeeds.

Inside, it also keeps a few memory flags, like sticky notes on the assistant’s desk: “Have I already restored once?”, “Am I mid-restore right now?”, and “Am I allowed to auto-save while the user edits?”

showSyncFailureToasts helper inside the file

If sending some rows to the server fails, this shows lasting error messages naming the failed device or template. The messages stay until the person closes them, because this is important: their notebook still has the work, but the official binder rejected part of the update.

Connected to Called by runModeASync when the sync file reports failures.
runModeASync helper inside the file

This is the “please update the official binder” step after a merge. It calls the sync file. If anything fails:

  • it rewrites the notebook with the draft we wanted to keep (so auto-save cannot overwrite good notes with a reverted screen),
  • it turns off quiet auto-save temporarily,
  • it asks the sync helpers to put failed rows back to official values on screen,
  • and it shows the error toasts.
Connected to Uses syncDraftToApi, revertFailedMaterialsToApi, and revertFailedTemplatesToApi. Used by both the first-load restore and the refresh-materials restore.
hydrateSessionFromDraft helper inside the file

This is the full open-page journey described earlier. It is careful to run only once when data is ready, and not to overlap with itself. It temporarily disables quiet auto-save while restoring, so a half-finished restore cannot be written back as if it were the user’s latest edits.

Connected to Calls draftStorage → reconcileMaterials → recreateOrphanCustomMaterials → reconcileTemplates → recreateOrphanTemplates → screen hydrate → draftStorage write → runModeASync.
reconcileAfterMaterialsRefresh public tool

Used when the person presses Refresh Materials. Official materials may have changed under them. This builds a notebook from the current screen (not only from storage), merges against the fresh official materials, recreates missing hand-added materials if needed, removes dead material links from templates, merges templates, updates the screen, and syncs again.

Connected to Uses buildDraftFromState first (to capture the live session), then the same merge / recreate / sync family as first load.
Quiet auto-save effect background behavior

After a successful restore, whenever materials/templates/instances change, wait briefly, snapshot with buildDraftFromState, write with draftStorage. This is the “while editing” behavior.

clearDraftAfterCreateAllSuccess public tool

Empties the notebook after a successful Create All. Also turns quiet auto-save back on, so a new round of edits can start a fresh notebook.

The filing cabinet — draftStorage

This file is the only one that directly touches the browser’s storage. Everything else asks this file to read, write, or erase. That keeps storage rules in one place.

Why a special key? The notebook name includes both the person and the project. That way, Person A’s unfinished work on Project 12 never collides with Person B’s work, or with Person A’s work on Project 99.

What each piece does

getDeviceInstanceDraftStorageKey public

Builds the notebook’s full name. If we do not know the user or the project, it returns an empty name on purpose, so the other functions refuse to read or write. Better to do nothing than save under the wrong label.

The parsers (isRecord, parseMaterialEntry, parseTemplateEntry, parseInstanceEntry, parseDraft) private helpers

Storage can contain junk: old formats, half-written data, or hand-edited values. These helpers carefully inspect each piece. Valid pieces are kept. Invalid pieces are skipped. If the whole notebook is the wrong version or badly shaped, the whole read is treated as “no notebook.”

They also tolerate older notebooks that pre-date newer fields. For example, if an older note does not say whether a material was hand-added, the parser assumes it was not, so we do not accidentally try to recreate something we cannot recreate safely.

Connected to Only used inside readDeviceInstanceDraft. No other file talks to the parsers directly.
readDeviceInstanceDraft public

Opens the notebook and returns a clean, structured copy — or “nothing found.” Never crashes the page if storage is blocked or the text is corrupt.

Connected to Used by the manager during first-load restore.
writeDeviceInstanceDraft public

Saves a notebook, stamps today’s time on it, and forces the current version number. Returns a simple yes/no so callers know if storage rejected the write (for example, the browser is out of space).

Connected to Used by the manager after merges, after failed syncs (to preserve the good notebook), and during quiet auto-save.
clearDeviceInstanceDraft public

Throws the notebook away. Used after Create All succeeds.

hasDeviceInstanceDraftContent public

Answers: “Is this notebook actually empty, or does it contain any materials, templates, or instance notes?” Useful when the page wants to know whether there is unfinished work worth mentioning.

createEmptyDeviceInstanceDraft public

Hands out a brand-new blank notebook object. Used when there is no saved notebook yet, so the merge steps still have a structure to work with.

Taking a snapshot — buildDraftFromState

This file answers one question: “If I had to write down the important unfinished choices from what is on the screen right now, what would I keep?”

It deliberately does not save everything. Things that can be recalculated later (like “remaining quantity after template usage”) are left out. The notebook stays small and focused on choices the person made.

What it saves

  • Materials: whether it is hand-added, chosen subclass, override tick, hide/show, plus enough identity details (description/make/model/quantity/base used) to recreate a hand-added material later if needed.
  • Templates: reference, description, parent subclass, instance count, sort order, and each child device’s link to a material plus friendly name and order.
  • Group instances: only when the person customized Group ID and/or Group Name. Auto-generated labels are not stored, because the page can rebuild those.
buildDraftFromState public

Walks the current materials, templates, and instances and builds the notebook object. While doing that it converts subclass names (what people see in dropdowns) into subclass IDs (what the notebook and server prefer). It also deletes instance notes that point at templates/indexes that no longer exist.

Connected to Uses subclassIds for name→ID conversion. Used by the manager during quiet auto-save and during refresh-materials (to capture the live session before merging).

Restoring group labels — applyInstanceDraft

Group Instances on the screen are mostly generated automatically from templates (one template with “3 instances” becomes three groups). But people can renumber or rename those groups. Those custom labels live in the notebook.

After the page regenerates the automatic groups, this file lays the custom labels back on top — like putting personalized sticky labels onto freshly printed folders.

applyInstanceDraft public

For each generated group, look up a notebook note using “template + instance number.” If the note says the Group ID was customized, use the saved Group ID. If the note says the Group Name was customized, use the saved Group Name. Otherwise keep the automatic value.

Connected to Used by the page’s main state flow after instances are derived. The notebook section it reads was earlier cleaned/remapped by the manager and the orphan-template helpers.

Merging materials — reconcileMaterials

This is the careful comparison between “what the person saved” and “what the office currently has” for Project Materials.

Why “merge” instead of “just reload the notebook”? Because the official list may have changed while the person was away. A material may have been deleted. A subclass may no longer exist. Blindly reloading the notebook could show ghost rows or invalid dropdown values. Merging keeps personal choices where safe, and drops or recreates where necessary.

What each piece does

canRecreateCustomMaterial private helper

Decides whether a missing hand-added material has enough trustworthy details to ask the server to create it again. Missing description/make/model, invalid subclass, or non-positive quantity means “do not recreate — just drop it.”

Connected to Used only by reconcileMaterials while sorting notebook-only materials into “prune” vs “orphan candidate.”
reconcileMaterials public

Produces four important outputs together:

  1. the materials list to show (official rows + personal overlays),
  2. IDs of materials that should be removed from templates,
  3. hand-added materials that should be recreated,
  4. the cleaned materials section of the notebook for the next save.

For materials that still exist officially, personal subclass / override / hide choices win, but identity fields like description come from the official row. That avoids showing stale names when the official binder was updated.

Connected to Uses subclassIds. Its orphan list is the input to recreateOrphanCustomMaterials. Its removed IDs tell the manager which template device links to strip during refresh.

Merging templates — reconcileTemplates

Same merge philosophy as materials, applied to Group Templates. Personal wording and structure from the notebook are preferred when the template still exists officially. Broken device links (pointing at materials that are gone) are cleaned out.

What each piece does

filterDevicesAgainstMaterials private helper

Keeps only child devices whose material still exists, then renumbers their order so there are no gaps.

Connected to Used inside reconcileTemplates both for still-living templates and for orphan candidates.
toUiDevices private helper

Converts the notebook’s device notes into the shape the on-screen template table expects.

reconcileTemplates public

Walks official templates first and overlays notebook details where present. Then looks for notebook templates that no longer exist officially. If such a template still has at least one valid device, it becomes an orphan candidate. If it has zero valid devices left, it is dropped quietly — there is nothing useful to recreate.

Connected to Uses subclass helpers. Its orphan list feeds recreateOrphanTemplates. Should run after materials orphans are recreated, so device links can already use new material IDs.
remapInstanceDraftKeys public

When a template is recreated, it gets a new ID. Group-instance notes are stored under keys like “oldTemplateId:2”. This helper rewrites those keys to “newTemplateId:2” so custom Group ID / Group Name notes stay attached to the right groups.

Connected to Used by applyOrphanRemapToDraft inside the templates recreate file.

Bringing deleted materials back — recreateOrphanCustomMaterials

Sometimes a hand-added material is in the person’s notebook but gone from the official list (deleted by someone else, or lost in an earlier failed flow). If we still have a full enough description of it, we ask the server to create it again.

Important: the recreated material is not the same row with the same ID. It is a new row with a new ID. So every place that remembered the old ID must be updated.

What each piece does

recreateOrphanCustomMaterials public

Goes through each orphan candidate one by one. Asks the server to create it. Builds the on-screen material row from the server response, then re-applies personal choices like override and hide. Collects successes (with old→new ID map) and failures.

Connected to Receives candidates from reconcileMaterials. Uses shared conversion helpers outside this folder to turn the server response into a screen row. Its results are immediately passed to applyCustomMaterialRemapToDraft.
applyCustomMaterialRemapToDraft public

Updates the notebook after recreate attempts:

  • failed old IDs are deleted from the notebook,
  • successful old IDs are removed and rewritten under the new IDs,
  • every template device in the notebook that pointed at an old ID is pointed at the new ID instead.
Connected to Always used right after recreateOrphanCustomMaterials inside the manager.
remapTemplateMaterialIds public

Same old→new material ID rewrite, but for the templates currently sitting in screen memory (not the notebook). Used on the refresh-materials path so the on-screen templates do not keep dead links while the next merge runs.

Connected to Used by the manager’s refresh flow, usually together with removing materials that were pruned and never successfully recreated.

Bringing deleted templates back — recreateOrphanTemplates

Same idea as materials orphans, but for Group Templates. If a template lives in the notebook and not on the server, and it still has valid devices, we rebuild it on the server in careful steps.

What each piece does

toSourceRow private helper

Turns one orphan notebook entry into a temporary on-screen-shaped template so the recreate steps can reuse the same field meanings the rest of the page understands.

Connected to Used only inside recreateOrphanTemplates. Uses subclass helpers to turn saved subclass IDs back into names.
recreateOrphanTemplates public

For each orphan, it follows a safe recipe:

  1. create a blank template on the server (gets a new ID),
  2. fill in reference / description / parent subclass / sort order,
  3. if filling in fails, delete the blank template so we do not leave junk behind,
  4. create as many child devices as we can from the remaining valid devices,
  5. record success (old ID → new ID) or failure.
Connected to Receives candidates from reconcileTemplates. Results go into applyOrphanRemapToDraft.
applyOrphanRemapToDraft public

Updates the notebook after template recreate attempts:

  • failed old template IDs (and their group-instance notes) are removed,
  • successful ones are rewritten under the new template ID,
  • group-instance notes are remapped with remapInstanceDraftKeys so custom labels follow the new template ID.
Connected to Depends on remapInstanceDraftKeys from the templates merge file. Called by the manager right after recreate.

Sending changes to the server — syncDraftToApi

After the screen has the merged truth, this file asks: “Which of these merged values are still different from the official binder?” Only those differences are sent.

It is intentionally cumulative and forgiving: it does not wait for a row to be perfect or complete. If a person chose a subclass and left a description blank, the subclass change can still be pushed. Failures are collected per row so one bad template does not block every other update.

What each piece does

materialNeedsSync / templateParentNeedsSync private helpers

Simple difference checks. Materials compare subclass, override, and hide/show. Template parents compare reference, description, parent subclass, and sort order. If nothing changed, no server call is made for that part.

syncDraftToApi public

Runs the material updates and template updates. For templates it may also:

  • delete child devices that exist officially but not in the merged screen row,
  • create child devices that exist on screen but not officially,
  • update child devices whose material link, friendly name, or order changed.

Everything is attempted; failures are remembered rather than throwing away the whole batch.

Connected to Uses subclass helpers and shared “build parent template update” logic from the Group Templates section. Called by the manager’s runModeASync.
revertFailedMaterialsToApi public

If a material update failed, put that material’s on-screen fields back to the official version. The notebook is intentionally left alone so a later refresh can try the personal values again.

Connected to Used immediately after syncDraftToApi inside the manager when failures exist.
revertFailedTemplatesToApi public

Same idea for templates. One special detail: the on-screen “instances” count is a session concept not owned the same way by the materials/templates APIs here, so that count (and whether the row is expanded) is preserved even when other fields revert.

Connected to Also used by the manager right after sync failures, together with the materials revert.

Name ↔ ID helpers — subclassIds

People see subclass names in dropdowns (“Door”, “Camera”). The notebook and many server calls prefer numeric IDs. This small file is the translator used all over the persistence flow.

resolveSubclassIdByName public

Given a visible name, find the matching ID. If the name is blank or unknown, return “no ID.”

Connected to Used by the snapshot builder (when saving) and by sync (when comparing/pushing material subclass changes).
resolveSubclassNameById public

Given an ID, find the visible name for dropdowns and labels. If the ID is missing, return “no name.”

Connected to Used by both merge files and by the template orphan recreate helper when rebuilding rows for the screen.
isSubclassIdValid public

Checks whether an ID still exists in the current official subclass list. “No subclass chosen” is allowed. An ID that no longer exists is not. This prevents the merge from re-applying a deleted subclass onto a row.

Connected to Used heavily inside both reconcile files (and when deciding whether a hand-added material can be recreated).

Quick memory sheet

  • Manager decides the order of operations and when auto-save is allowed.
  • Filing cabinet is the only door to browser storage.
  • Snapshot builder copies important unfinished choices from the screen into notebook shape.
  • Merge files combine notebook + official data and discover what must be dropped or recreated.
  • Recreate files rebuild missing hand-added materials / templates and fix all the ID links afterward.
  • Sync file pushes remaining differences to the official binder and supports graceful fallback when a row fails.
  • Apply instance draft puts personalized group labels back onto auto-generated groups.
  • Subclass helpers translate between human-readable names and system IDs for everyone else.
One sentence to remember This folder is the page’s memory: it quietly notes unfinished work, restores it against the latest official data when the person returns, repairs broken links when it can, and updates the official records row by row without demanding the whole form be perfect first.
