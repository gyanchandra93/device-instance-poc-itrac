Device Instance Utility · Spec

LocalStorage Persistence Plan

Draft-overlay persistence for Project Materials (PM), Group Templates (GT), and Group Instances (GI). LocalStorage is scoped by login user ID + project ID, always wins over API for persisted user choices, and is cleared only after a successful Create All API call.

1. Goal & priority rule

Persist the user’s in-progress work across page refresh and Refresh Materials until they click Create All and that API call succeeds. Another user with the same project ID but a different login must never see this draft.

Priority (non-negotiable) For every field we choose to persist:
Display = LocalStorage (if present & still valid) → else API / auto-derived
  • LS data = highest priority for persisted fields.
  • Derived fields (Used, Remaining, status counts, Live Preview) are never stored.
  • Display names (device name, subclass name) are never stored — only IDs; names resolve from latest API lists.

2. Storage key & shape

Key

deviceInstanceUtility_{userId}_{projectId}
  • userId from existing localStorage.userId / getUserId()
  • projectId from route params
  • If userId is missing → do not read/write LS (session-only fallback)

Draft payload (single JSON blob)

type DeviceInstanceUtilityDraft = {
  version: 1;
  updatedAt: string; // ISO timestamp
  projectMaterials: {
    [deviceId: string]: {
      subclassId: number | null; // user choice; resolve name from latest subclass list
      isOverride: boolean;       // Override acknowledgment — LS wins
      isHidden: boolean;         // Actions hide/show — LS wins
    };
  };
  groupTemplates: {
    [templateId: string]: {
      reference: string;
      description: string;
      parentSubclassId: number | null;
      instances: number;
      devices: Array<{
        id: string;                 // device row id (server or local)
        materialId: number;         // FK to PM device id
        friendlyDescription: string;
        sortOrder: number;
      }>;
      // NOT stored: Devices count, Remaining, Status
    };
  };
  groupInstances: {
    // ONLY when user renumbered or manually edited Group ID / Group Name
    [instanceKey: string]: {      // key = `${templateId}:${instanceIndex}`
      groupId?: string;
      groupName?: string;
      isGroupIdCustom: boolean;
      isGroupNameCustom: boolean;
    };
  };
};
Why one blob? Atomic clear on Create All success, one version field, and consistent PM ↔ GT ↔ GI pruning.

3. Lifecycle overview

Event Behavior
First visit (no LS) Seed UI from API only (current behavior).
Page refresh / revisit Fetch API → reconcile with LS → render available LS+API values → run cumulative LS→API sync per dirty row.
Refresh Materials button Same as page refresh path for PM (+ cascading prune into GT/GI). Then cumulative sync.
Normal edits after render/sync Preserve today’s behavior (e.g. blur on Reference → immediate update API). Also debounce-write React state → LS.
Create All success Clear React draft effects + removeItem for that user+project key.
Create All failure Do not clear LS.
Logout Do not clear DIU LS (kept until Create All succeeds).

4. Project Materials (PM)

What to store

Field Persist? Display / calculation rule
Device ID Yes (map key) Must exist in latest PM API list. If missing → remove device + related details from LS and remove that device from every GT that references it. Never recreate a missing PM device from LS.
Device name / make / model / ppmQty / status No Always from latest API. GT device name display also resolves from latest PM list via device id.
iTrac Subclass Store subclassId only If id missing from latest GetProjectSubclasses → delete from LS and all occurrences (PM + GT parent subclass). If valid → show latest name for that id.
Override Yes (isOverride) LS always takes precedence over API.
Used No Dynamic: baseUsed (API) + Σ(GT instances count for templates that include this device)
Remaining No Dynamic: ppmQty (latest API) − Used (dynamic)
Actions (Hide / Show) Yes (isHidden) LS overrides API visibility. See Actions behavior below.
All other columns No Latest API values only.

Actions column behavior (Hide / Show)

  1. Clicking Hide partially greys out the row. User can still edit that PM row. Action label becomes Show.
  2. While greyed/hidden: if header checkbox Show hidden (n) is unchecked, the row becomes fully invisible in the PM table.
  3. While greyed/hidden: that device is removed from the GT child-row device Select dropdown in every template.
  4. Clicking Show removes the grey-out and restores dropdown eligibility.

Non-PPM materials

Same LS rules apply (subclass / override / hide) until Create All succeeds.

5. Group Templates (GT)

What to store

  • reference
  • description
  • parentSubclassId (id only; resolve latest name)
  • instances
  • Devices: materialId + friendlyDescription (+ row id / sortOrder)
  • groupTemplateId as map key (for tracking / remapping)

What NOT to store

  • Devices count
  • Remaining
  • Status
  • Device display names (always resolve from latest PM via materialId)

Hydration / display rules

  1. Load GT from API as base.
  2. Overlay LS by template id — LS field values win when present.
  3. For each device line:
    • If materialId not in current PM → drop device + friendly name from that GT (and LS).
    • If it exists → LS friendly name wins; device name shown from latest PM description for that id.
  4. Parent subclass: resolve id → latest name; if id gone → clear parent subclass in UI + LS.
“Last editor on this machine” intent User A’s LS keeps their edits even if User B changed the server template. When User A returns, their draft overlays API for their session.

Orphan template (in LS, deleted on API)

  1. Confirm template id is absent from latest GT API list.
  2. Recreate via API as a brand-new template using LS details, but only using devices that still exist in PM.
  3. If some devices are missing: create the new template with the remaining existing devices (do not require all devices).
  4. If no linked devices remain in PM: do not recreate (drop orphan restore).
  5. Replace old template id in LS + React state with the new generated id.

Note: PM devices themselves are never recreated from LS when missing from API.

6. Group Instances (GI)

Write GI to LS only when user explicitly customizes Renumber Selected, or manual Group ID / Group Name edits. Pure auto-generated GI from GT activity is never saved.

Identity key

${templateId}:${instanceIndex}

Stable across reload even if the in-memory UUID is regenerated. Matches existing syncInstancesFromTemplates matching strategy.

Read / merge

  • Whenever GT instances > 0 regenerates GI rows: build auto rows from GT first.
  • If LS has an entry for that instance key → LS groupId / groupName always override auto values; set custom flags accordingly.
  • If no LS entry for renumber / manual Group ID / Group Name → show automatic default data derived from GT changes.
  • When instance count drops → prune LS GI keys whose instanceIndex is out of range.

API sync

No GI API yet. GI LS is display/draft overlay only — no cumulative GI API sync on refresh.

7. Live Preview

No LocalStorage. Group Instances table (with LS overlays where applicable) drives preview automatically via existing derivation.

8. Cumulative LS → API sync

When this runs (only these moments)
  1. User refreshes the page (initial load with LS present)
  2. User clicks Refresh Materials
It does not replace normal per-field update behavior after the page has rendered.

What “cumulative” means

  • Per row, one API call carrying all available fields for that row (not one HTTP call per field).
  • PM: 1 material row → 1 patch/update call.
  • GT: 1 template row → 1 cumulative update call for that template (parent + its device ops as required by existing APIs).
  • Run row calls in parallel via Promise.allSettled (not one mega-payload for the whole section — current APIs are per-id).

Do NOT wait for every field to be non-empty

Trigger rule After UI has finished filling/rendering the merge of available LS values + available API values for that row, fire the cumulative call for that row.

Example: LS has Reference + Parent Subclass; API has Friendly Name; Description is empty in both → still sync immediately with whatever is available. Empty Description must not delay the call.

Recommended call strategy

Option Decision
1 single API call for all PM rows / all GT rows Not recommended — no bulk endpoint today; harder partial-failure handling.
1 cumulative call per row, parallelized Chosen — matches existing APIs; isolates failures; supports the toast rules below.

9. Normal editing after sync (preserve current behavior)

Once LS/API data are rendered and the load/refresh cumulative sync attempts are done, user activity must keep the pre-LS update behavior:

  • Change Reference on template 1 → lose focus → update API fires immediately (as today).
  • Same for other existing blur/immediate update paths in PM and GT.
  • Every meaningful edit also debounced-writes into LS so refresh can restore the draft.
Two modes, one page
Mode A — Load/Refresh: cumulative per-row LS→API sync.
Mode B — Interactive editing: existing immediate/blur updates + LS write-through.

10. Failure handling & toasts

If a cumulative update/patch fails after loading from LS, and the corresponding id still exists on the API:

  1. Populate that row in the UI from API data (not the failed LS overlay for that row).
  2. Keep LS draft unchanged so a later refresh can retry.
  3. Warn the user with a sticky toast (see below).

Toast content

Project Materials failure Include device name + device id with an appropriate message that sync from draft failed and they should refresh the page to retry applying LS.
Group Template failure Include template name + template id with an appropriate message that sync from draft failed and they should refresh the page to retry applying LS.

Toast dismiss behavior

Sticky until manual close If there is any failure toast from this sync path, it must not auto-hide. It closes only when the user clicks the toast close (×) icon.

11. When LS is cleared

Situation Clear LS?
Create All API success (ResponseCode === true) Yes — entire draft for that userId + projectId
Create All API failure No
Page refresh / Refresh Materials No (reconcile/prune only)
Logout No (explicit product decision for now)
Partial cumulative sync failure No — keep draft for retry

12. Orphan / deleted-entity rules (summary)

Case Action
PM device in LS, missing from API Remove from LS; strip from all GT device lines. Never recreate device.
Subclass id in LS, missing from subclass API Delete from LS and all occurrences (PM + GT parent subclass).
GT in LS, missing from API; ≥1 devices still in PM Create new template with remaining existing devices; remap id in LS.
GT in LS, missing from API; zero devices left in PM Do not recreate; drop orphan restore.
GT device materialId missing from PM Drop that device (+ friendly name) from the template/LS only.
